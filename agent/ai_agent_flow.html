五、架构评审：结构性缺陷与补强建议

P0 · 结构断裂
分层引擎与A00之间没有明确的调用协议
分层引擎是一个独立文档（SKILL），A00是一个独立Agent。但谁来调用分层引擎？文档里A00只写了"信号路由"能力，没有写"对学员执行三轴评分并输出T型标签"。A01的"初识摸底"阶段也没有写明"调用分层引擎进行判定"。

结果：分层引擎的判定树悬在半空，没有任何Agent显式声明"我负责执行它"。
建议：明确指定：A00负责持续信号采集 → A01在首次建档时调用分层引擎完成初判 → A00在后续监控中触发迁移规则时再次调用分层引擎进行标签更新。写入各自的Agent文档中。
P0 · 能力缺口
缺少一个"复购/续费转化"Agent 或模块
A01覆盖"体验营→正价课"的首次转化链路。A02覆盖就业变现。但正价课结业后的复购升仓（推L2/L3/跨品类课程）由谁来驱动？

A01文档只提到"在学员状态好、满意度高的时候自然推荐"——这是一个模糊指引，不是结构化策略。考虑到复购是2026年"挺进大别山"战役的核心杠杆之一（订单复购率提升20%），这个环节不能只靠A01的自由裁量。

建议：要么在A01中增加一个显式的"复购决策模块"（含升仓时机判定、拒卖熔断条件、跨品类推荐优先级），要么拆分出一个A04复购运营Agent。前者更简洁，推荐前者。
P1 · 数据断链
A01的"学员档案"没有定义数据结构
A01文档反复强调"持续更新学员档案"，但没有定义这份档案包含哪些字段、什么格式、存在哪里。分层引擎输出的ABCD标签/T型原型/IPD配方，要存入这份档案吗？A02需要读取这份档案来评估就业能力吗？A03需要读取来做审查吗？

结果：四个Agent各自为政，缺乏统一的数据底座。
建议：定义一份《学员主档案》的Schema（至少包含：基础信息、ABCD标签、T型原型、三轴评分、IPD当前配方、学习进度、情绪轨迹、复购历史、A03审查记录），作为所有Agent的共享读写对象。
P1 · 职责冲突
A03编号混乱 + 审查范围与A00存在重叠
文件名是"A03_教务督导"，但文件内部标题写的是"A05"。更关键的是：A00的信号检测能力（情绪突变、行为模式异常）和A03的服务质量审查能力存在功能重叠——比如"学员发出退费信号"，到底是A00先检测然后通知A01处理，还是A03审查后认定是A01服务失误？

建议：明确边界——A00只看学员侧信号（学员说了什么、做了什么），A03只看服务侧质量（员工/Agent回了什么、做了什么）。两者的信号源不同，不应重叠。
P1 · 执行空白
群运营能力在Agent体系中完全缺位
分层引擎里大量原型的服务策略依赖群环境：T1需要"在群里发号施令"、T7需要"闲聊房"、混合体2号需要"老乡会"、混合体4号需要"Pia戏组局"。但四个Agent没有任何一个的职责包含"群氛围运营/群内容策划/群场景搭建"。

A01是一对一服务角色。A00是后台监控。A02是就业对接。A03是审查。
谁来管群？

建议：A01需要增加"群场景运营"能力模块，或者引入一个轻量级群运营Agent。否则分层引擎里一半的IPD配方（C模块、D模块）在实际执行时找不到责任主体。
P2 · 冷启动问题
A00的"持续运行"特性在技术实现上未定义
A00被定义为"一直醒着的"——但大模型Agent并不天然具备7×24小时持续监听消息流的能力。这需要的是一个事件驱动的中间件（消息队列→规则引擎→LLM按需调用），而不是一个"Always-on Agent"。

建议：将A00拆分为两层：①轻量级规则引擎（关键词匹配+行为频率统计，不用LLM，跑在企微消息webhook上）；②LLM深度分析模块（仅在规则引擎触发预警后被唤醒做深层判断）。这样成本和延迟都可控。
